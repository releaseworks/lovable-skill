# Releaseworks Backup — Edge Function Contract

> Status: Design v1
> Audience: implementers of the `rw-backup` Supabase Edge function (installed into the
> **customer's** Lovable project by the Releaseworks skill) and of the backend
> client that calls it.
>
> A complete, deployable reference implementation of this contract (Deno/
> TypeScript) is in [`edge-function-reference.md`](edge-function-reference.md).

## 1. Overview

The `rw-backup` Edge function is deployed **inside the customer's own Lovable
Cloud (Supabase) project** by the Releaseworks skill. It is the only component
that can read the customer's data, and it exists solely to let the Releaseworks
backend extract a logical backup of the project's `public` schema.

- **Direction:** Releaseworks backend → customer Edge function (pull). The Edge
  function never initiates calls to the backend.
- **Privilege:** runs with the Supabase **service role** (bypasses RLS) but is
  **read-only** — it only ever issues `SELECT` / catalog queries.
- **Scope (v1):** `public` schema only — table DDL + row data. No storage
  buckets, no `auth.*`, no secrets, no Edge function source. (See backup-scope
  decision.)

Because this endpoint can read the entire database, its authentication is
defense-in-depth: **every request must pass both a per-source bearer token and
an asymmetric signature** (see §3).

## 2. Configuration (Supabase secrets in the customer project)

Set by the skill at install time:

| Secret | Meaning |
|---|---|
| `RW_SOURCE_ID`   | Backend-issued source identifier, e.g. `src_a1b2c3`. Echoed in responses for sanity checks. |
| `RW_TOKEN`       | Per-source shared secret (32-byte CSPRNG), generated by the backend. Bearer credential. |
| `RW_PUBLIC_KEY`  | Releaseworks' ECDSA P-256 **public** key (PEM). Used to verify request signatures. |

The Edge function never needs the backend URL — it only ever responds.

## 3. Authentication & request integrity

Every request from the backend carries:

| Header | Description |
|---|---|
| `Authorization: Bearer <RW_TOKEN>` | Proves the call is authorized for *this specific source*. Revocable per source. |
| `X-RW-Timestamp` | Unix seconds when the request was signed. |
| `X-RW-Signature` | Base64url ECDSA-SHA256 signature over the canonical string (below), made with the Releaseworks **private** key. |

### 3.1 Canonical string

The backend builds, and the Edge function reconstructs, exactly:

```
{METHOD}\n
{PATH}\n
{CANONICAL_QUERY}\n
{X-RW-Timestamp}\n
{SHA256_HEX(body)}
```

- `METHOD` — upper-case HTTP method (`GET`).
- `PATH` — request path, no host, no query (e.g. `/functions/v1/rw-backup/data`).
- `CANONICAL_QUERY` — query params sorted by key, `k=v` joined by `&`,
  percent-encoded. Empty string if none.
- `SHA256_HEX(body)` — hex SHA-256 of the raw request body; for GET (empty body)
  this is the SHA-256 of the empty string.

### 3.2 Verification order (fail closed)

The Edge function MUST verify, in order, and reject on first failure:

1. `Authorization` bearer equals `RW_TOKEN` — **constant-time** compare. → `401 unauthorized`
2. `|now - X-RW-Timestamp| <= 300` seconds. → `401 timestamp_skew`
3. `X-RW-Signature` verifies against `RW_PUBLIC_KEY` over the reconstructed
   canonical string. → `401 invalid_signature`

**Why both factors:** the bearer token proves the customer authorized this
install (and lets us revoke one source); the signature proves the request truly
came from Releaseworks. A leak of our token store still can't forge a signature;
a leak of our private key still can't pass without the per-source token.

### 3.3 No replay nonce (v1)

There is deliberately **no nonce / replay-protection store** in v1. The endpoint
is strictly read-only over TLS, so a replayed request only re-reads data the
attacker (who must already be on the wire to capture the signed request) would
have seen in the original response. The signature prevents forgery and the
±300s timestamp window bounds validity; adding a nonce would require writable
state in the customer project and a read+write on every paginated call for
negligible gain. Reintroduce a nonce only if a state-changing (write/restore)
operation is ever added to this function — see decision D2.

## 4. Endpoints

Base path: `/functions/v1/rw-backup`

### 4.1 `GET /schema`

Returns the structure needed to reconstruct the schema and to drive data
extraction.

**Response 200**

```json
{
  "schema_version": 1,
  "source_id": "src_a1b2c3",
  "generated_at": "2026-06-23T03:00:00Z",
  "restore_order": ["users", "projects", "tasks"],
  "tables": [
    {
      "name": "users",
      "primary_key": ["id"],
      "create_ddl": "CREATE TABLE public.users (...);",
      "post_ddl": ["CREATE INDEX ...;", "ALTER TABLE ... ADD CONSTRAINT ... FOREIGN KEY ...;"],
      "fk_dependencies": [],
      "columns": [
        { "name": "id",         "pg_type": "uuid",        "encoding": "text" },
        { "name": "email",      "pg_type": "text",        "encoding": "text" },
        { "name": "avatar",     "pg_type": "bytea",       "encoding": "base64" },
        { "name": "prefs",      "pg_type": "jsonb",       "encoding": "json" },
        { "name": "created_at", "pg_type": "timestamptz", "encoding": "text" }
      ],
      "approx_row_count": 1280
    }
  ]
}
```

Notes:
- `restore_order` is a FK-safe topological order of table creation/insertion.
  Foreign-key constraints are emitted as `post_ddl` (applied after all data) so
  that the eventually-consistent, possibly-cross-table-inconsistent dump (see
  consistency decision) can still load; the manifest records the inconsistency
  window for the restorer.
- `create_ddl` covers columns + PK + NOT NULL/defaults. Indexes and FKs go in
  `post_ddl`.
- `encoding` tells the backend how each value is JSON-encoded in `/data` (see
  §5). This is how we preserve type fidelity through JSON.

### 4.2 `GET /data`

Keyset-paginated row extraction for one table.

**Query parameters**

| Param | Required | Description |
|---|---|---|
| `table` | yes | Table name from `/schema`. |
| `after` | no  | Last primary-key value from the previous page. Omit for the first page. |
| `limit` | yes | Max rows to return (backend sets fixed v1 page size, e.g. 500). |

Pagination is **keyset**: `... WHERE pk > :after ORDER BY pk ASC LIMIT :limit`
(composite PKs ordered lexicographically). No `OFFSET`. This is what makes the
extraction safe to restart and free of skip/duplicate within a table.

**Response 200**

```json
{
  "table": "users",
  "rows": [
    { "id": "0001...", "email": "a@b.com", "avatar": "aGVsbG8=", "prefs": {"x":1}, "created_at": "2026-01-01T00:00:00Z" }
  ],
  "last_id": "0001...",
  "has_more": true,
  "page_bytes": 81234
}
```

- Values are encoded per the column `encoding` from `/schema`
  (`text` → string, `base64` → string, `json` → embedded JSON).
- `last_id` is the cursor to pass as `after` on the next call (PK of the last
  row). For composite PKs it is an array.
- `has_more` is `true` when a full page was returned and more rows may exist.
- `page_bytes` is advisory (lets the backend watch payload growth).

### 4.3 Read-only guarantee

The function MUST only execute `SELECT` and catalog reads. It never writes to
the customer's database at all — there is no nonce table or any other writable
state (see §3.3).

## 5. Type encoding conventions

To survive JSON transport without losing fidelity:

| pg_type family | `encoding` | JSON form |
|---|---|---|
| text/varchar/uuid/numeric/timestamp(tz)/date/bool/int | `text` | string (numbers/bools may be native; backend treats `encoding` as source of truth) |
| `bytea` | `base64` | base64 string |
| `json` / `jsonb` | `json` | embedded JSON value |
| arrays | `text` | Postgres array literal string (e.g. `{1,2,3}`) |
| `NULL` (any) | — | JSON `null` |

The backend uses `encoding` + `pg_type` to emit correctly-typed, correctly-quoted
`INSERT` values in the `.sql` dump.

## 6. Errors

All errors are JSON: `{ "error": { "code": "...", "message": "..." } }`.

| HTTP | code | When |
|---|---|---|
| 401 | `unauthorized` | bad/missing bearer token |
| 401 | `timestamp_skew` | timestamp outside ±300s |
| 401 | `invalid_signature` | signature verification failed |
| 404 | `table_not_found` | `table` not in `public` schema |
| 400 | `bad_request` | missing/invalid params |
| 429 | `rate_limited` | self-imposed or Supabase throttle; backend should back off and retry |
| 500 | `internal` | unexpected; backend treats as retryable |

CPU-limit aborts in the runtime surface as a dropped/5xx response; the backend
treats these as retryable and (in v1) restarts the whole job (restart-only,
atomic-publish decision). Keeping `limit` small is what keeps each invocation
under the CPU budget.

## 7. Non-goals (v1)

- No resume token / server-side job state (the backend drives pagination).
- No storage/auth/secrets export.
- No write/restore endpoint — restore is download-only on the backend side.
- No adaptive page sizing — the backend sends a fixed `limit`.
